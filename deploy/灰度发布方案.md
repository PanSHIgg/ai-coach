# 灰度发布方案（Phase 5 / F9）

> 真源：`docs/split/08-部署与运维.md` §10.4/§10.6/§10.7。
> 目标：在「生产环境稳定运行 7 天无 P0、监控告警生效」的 M5 退出标准下，安全上线。
>
> **本沙箱限制（如实标注）**：无 Docker（缺 CAP_SYS_ADMIN，容器无法运行），
> `docker compose config` / `docker compose up` 均不可用，`promtool` 未安装。
> 故本方案为**可执行清单 + 判据**，脚本命令需在具备 Docker 的 staging/生产主机上执行；
> 本仓已交付的 compose / Prometheus / Grafana / nginx / CD 产物均只做了**静态校验**。

---

## 1. 发布流程（总览）

```
打 tag(v*) 或 手动触发
  → CI 全绿（lint + pytest + 前端构建）
  → CD build：docker build（tag = git short sha，见 deploy/docker-compose.yml ${GIT_SHA}）
  → 推送镜像仓（占位）
  → staging：alembic upgrade head → 部署 → 冒烟
  → prod 审批（GitHub Environment 人工放行）
  → prod 备份 → alembic → 灰度放量 → 观察 → 全量
  → 稳定观察 7 天 → Go/No-Go 复盘
```

关键纪律：
- **镜像打 git short sha**（`GIT_SHA`），回滚即切回上一 sha 镜像（§10.6）。
- **先建后改**：迁移只加字段/表，不删不改列，保证可回滚（§10.5/§10.6）。
- **先 staging 后 prod**：迁移与冒烟在 staging 通过再进 prod。
- 接口冻结（F2）后，发布窗口不夹带契约变更。

## 2. 灰度比例与放量策略

| 阶段 | 流量比例 | 时长（建议） | 放量条件 |
| --- | --- | --- | --- |
| Canary | 10% | ≥30 min | 错误率 <1%、P95 达标、无 P0/P1 |
| 扩容 | 50% | ≥30 min | 同上，且 AI 成本速率正常 |
| 全量 | 100% | — | 同上，观察进入 7 天稳定期 |

放量维度（按实现能力二选一）：
1. **实例级**：多副本时先替换 1/10 副本（`docker compose up -d --scale api=N` 配合 Nginx upstream 权重或滚动替换）；
2. **用户级**：按 user_id 哈希取模（10% → 50% → 100%），需在网关/后端灰度开关处实现。

放量节奏：每档至少观察 30 分钟（覆盖一个完整业务周期），任一档触发回滚条件即**立即停止放量并回滚**。

## 3. 回滚触发条件与步骤

### 3.1 触发条件（满足任一即回滚）

| 条件 | 判据 |
| --- | --- |
| 服务不可用 | `up{job="ai-coach-api"} == 0` 持续 ≥5 min（对应告警 `ServiceDown`） |
| 错误率超标 | 5xx 占比 >5% 持续 ≥5 min（对应告警 `HighErrorRate`） |
| 延迟劣化 | 接口 P95 > 1s 或 AI P95 > 3s 持续 ≥10 min |
| 数据错误 | 热量/账户金额对拍出现系统性偏差（非个例） |
| 迁移引发 | db 报错、关键表行数异常下降或写入失败 |
| AI 成本失控 | 24h 成本估算超预算（对应告警 `AIBudgetExceeded`） |

### 3.2 回滚步骤

```bash
# 1) 切回上一 sha 镜像（compose 用 GIT_SHA 指定 tag）
cd /srv/ai-coach
GIT_SHA=<上一版本 short sha> docker compose -f deploy/docker-compose.yml up -d

# 2) 校验健康与版本
curl -fsS https://your.domain.com/healthz

# 3) 若本次含迁移：迁移只加字段 → 应用回滚后旧版本可忽略新列，无需回退；
#    若为不可逆变更，执行反向迁移脚本（本方案约定首期不做不可逆变更）
#    alembic downgrade -1
```

回滚后：保留现场（日志 + `/metrics` 快照）、定位根因、补热修、重走发布流程。

## 4. 稳定运行 7 天 · 观测项与判据（Go/No-Go 依据）

| # | 观测项 | 数据来源（Prometheus 指标 / 端点） | 判据（7 天） |
| --- | --- | --- | --- |
| 1 | 可用性 | `up{job="ai-coach-api"}`；`ServiceDown` 告警 | 无 5min+ 不可用；可用性 ≥99.9% |
| 2 | 错误率 | `http_requests_total{status=~"5.."}` / 总数 | 5xx 占比 <1%，且无 `HighErrorRate` 触发 |
| 3 | QPS 与容量 | `rate(http_requests_total[1m])` | 峰值 QPS 无异常跌零/抖增 |
| 4 | 接口延迟 | `http_request_duration_seconds`（P95/P99） | 查询 P95<300ms、写+重算 P95<800ms |
| 5 | AI 延迟 | `ai_calls_total` 配合日志耗时 | AI P95<3s，降级率（degraded=true）在阈值内 |
| 6 | 热量计算耗时 | `calorie_calc_seconds`（P95） | P95 稳定、无劣化趋势 |
| 7 | AI 成本 | `ai_cost_usd_total` / `ai_calls_total` | 日成本不超预算，无 `AIBudgetExceeded` |
| 8 | 磁盘 | `node_filesystem_*`（需外部 node_exporter） | 使用率 <80%，无 `DiskUsageHigh` |
| 9 | 日志链路 | JSON 日志含 `request_id`；落盘 `/var/log/app` | request_id 可串联；无异常堆积；保留 30 天 |
| 10 | P0/P1 缺陷 | 缺陷跟踪 | 7 天内 **0 个 P0**、P1 全部闭环 |
| 11 | 数据正确性 | 热量对拍、订单/核销核对 | 无系统性偏差 |

> 观测项 8 依赖外部 `node_exporter`（本仓 compose 未内置）；接入方式见 `deploy/README.md`。

## 5. 可执行清单（在具备 Docker 的主机逐条执行）

```bash
# 0) 前置：CI 全绿；已在 staging 通过
# 1) 备份
ssh $PROD "pg_dump ... > /backup/ai_coach_$(date +%F_%H%M).sql"
# 2) 拉新镜像并部署（tag=git sha）
GIT_SHA=$(git rev-parse --short HEAD) docker compose -f deploy/docker-compose.yml up -d --build
# 3) 迁移（只加字段）
docker compose -f deploy/docker-compose.yml exec -T api alembic upgrade head
# 4) 健康 + 指标
curl -fsS https://your.domain.com/healthz
curl -fsS http://api:8000/metrics | head     # 容器网络内直连
# 5) 灰度放量（10% → 50% → 100%），每档观察 ≥30min，对照 Grafana 看板
# 6) 7 天观测（对照 §4 判据），无 P0 则 Go
```

**验收结论口径**：以上 §4 全部达标且 7 天无 P0 → **Go**；任一项不达标 → **No-Go** 并回滚定位。
