# 第一部分：项目概述

## 1.1 背景

国内成人超重率 34.3%、肥胖率 16.4%，合计超重肥胖人群超 6 亿。体重管理市场已超 3260 亿元，年均复合增长率 15% 以上。但超 7 成人主动尝试过体重管理，仅 19.3% 能达成目标，6 成年轻人在 3 个月内放弃。核心矛盾是"知道该做，但做不到"——用户缺的不是记录工具，而是每一次饭点、每一次饥饿、每一次动摇时主动介入的 AI 教练。

## 1.2 项目目标

做一个微信小程序（首期）+ 后续原生 App 预留的体重管理平台，核心能力：

1. **热量账户**：以"摄入 - 消耗 = 缺口"为底层逻辑，首页环形图展示今日还能吃多少，拍照即记录。
2. **AI 饭点决策引擎**：食堂/外卖/便利店场景下拍照菜单，AI 推荐最优组合并一键记录。
3. **AI 主动介入**：覆盖 12+ 触发场景（餐前提醒、下午茶防诱惑、深夜防崩塌、超标后运动建议等），通过订阅消息推送。
4. **AI 对话咨询**：回答"饿了能吃什么""这菜油多吗""今天为什么没瘦"等问题，邀请扩容机制。
5. **运动与能量消耗**：步数同步、运动记录、TDEE 模型（BMR+NEAT+EAT+TEF）、步数校准。
6. **五种社交**：监督、兴趣社群、约战、挑战赛、动态。
7. **商家标准化生态**：标准目录制 + 价格区间制 + 统一券池 + 商家极简后台。
8. **分层收费 + 邀请解锁**：基础免费 / 进阶 29 元 / 高级 59 元 / 最高档终身，全部可邀请解锁。

## 1.3 目标用户

| 用户群       | 核心痛点             |
| --------- | ---------------- |
| 职场白领      | 不知道吃啥、饿了扛不住、没空运动 |
| 学生党       | 食堂不透明、夜宵诱惑、没人监督  |
| 反复减肥失败者   | 管不住嘴、坚持不了        |
| 中老年慢病人群   | 不知道怎么吃、需要简单+有人盯着 |
| 健身增肌/减脂人群 | 营养运动要配合、需要精确数据   |

## 1.4 项目范围（首期 MVP）

**要做**：微信小程序用户端全部功能 + 后端全套服务 + 管理后台（商家端+平台端合并，先做轻量版）+ 数据库 + 部署上线。

**不做（二期）**：原生 App、iOS/Android 双端、开放平台、多语言、国际化、小程序外的其他形态。

## 1.5 不做清单（明确排除）

- 不做医疗诊断、不开处方、不替代医生。【假设】所有 AI 输出均带"仅供参考，具体请遵医嘱"免责声明。
- 不做在线支付以外的结算（如线下现金、转账）。
- 不做自营电商仓储物流，只做 CPS 导流 + 券核销。
- 不做视频直播、不做 IM 实时音视频（人工教练用异步工单消息，不发语音/视频）。
- 不做复杂权限体系（首期只有用户/商家/平台运营三种角色，不做 RBAC 多角色动态授权）。
- 不做多门店连锁的深度 ERP（商家只管自己门店的上品、定价、券、订单）。

## 1.6 关键业务指标（开发阶段需埋点）

新用户 7 日留存 > 25%、邀请 K 因子 > 0.5、商家扫码转化率 > 15%、拍照识别成功率 > 85%、AI 问答满意度 > 4.5/5、内容获客成本 < 20 元/人。

# 第二部分：产品需求 PRD

## 2.1 功能清单与优先级

**P0（必须，首期交付）**：微信登录、身体档案建档、热量账户首页、拍照记录、饮食记录 CRUD、运动记录、步数同步、TDEE 计算、AI 对话（含次数限制与邀请扩容）、饭点决策（菜单拍照识别+推荐）、商家列表与详情、标准 SKU 目录、券池（用户领券/用券）、订单（创建/支付/核销）、体重记录与趋势、提醒订阅、邀请裂变、社区动态与五种社交（基础版）、管理后台（用户/商家/订单/券基础管理）、埋点上报。

**P1（上线后 1 个月内）**：人工教练工单、平台自营 AI+真人教练订阅付费、商家权重排名、智能推荐、热力与报表后台、社区内容审核。

**P2（后续）**：数据飞轮微调、开放 API、原生 App。

## 2.2 角色与权限

| 角色        | 能做什么                                                  |
| --------- | ----------------------------------------------------- |
| 普通用户（C 端） | 记录、查看热量账户、AI 对话、查看/下单商家、社交、邀请、领券用券                    |
| 商家        | 登录商家后台、选品、在区间内定价、选券、上架/下架、查看核销、处理预约                   |
| 平台运营      | 管理后台全部：标准目录维护、商家入驻审核、价格区间设置、券池管理、内容审核、订单监控、数据看板、补贴券发放 |
| 真人健身教练    | 登录教练端、查看被分配用户的档案与记录、回复工单、复核方案、发动态                     |

## 2.3 核心业务流程

### 2.3.1 主流程：建档 → 每日使用 → 形成闭环

1. 微信授权登录 → 完善身体档案（性别/身高/体重/年龄/目标/活动水平） → 系统计算 BMR、目标热量预算、每日目标步数。
2. 每日早晨：首页弹"今天什么状态"（卧床/久坐/轻度/中度/高度五选一），或用户不点则用默认 PAL。
3. 每日 3-5 次：拍照记录饮食 → 视觉识别 → 用户确认/修正分量 → 写入摄入 → 热量账户环形图实时更新。
4. 饭点（11:00、17:00）推送：引导拍照或 AI 推荐。
5. 运动中/后：步数自动同步、手动添加运动 → 写入消耗 → 环形图"收入项"增加。
6. 深夜推送：当日缺口达成提醒 + 防崩塌话术。
7. 每周生成热量控制周报（含缺口、步数、体重趋势、AI 点评）。

### 2.3.2 商家下单流程

拍照/菜单识别/标准 SKU/附近商家 → 商家详情页 → 选标准 SKU 或菜品 → 确认订单（校验价格区间、选择可用券）→ 微信支付 → 到店出示核销码 → 商家扫码核销 → 订单完成 → 商家获贡献分 + 摄入记录自动写入 + 生成社区经验卡。

### 2.3.3 邀请裂变流程

用户分享带参二维码 → 被邀请人注册并完善档案 → 双方各得券；邀请人累计达 2/5/10 人分别解锁进阶版 90 天/180 天/永久（最高档终身教练）。【假设】防刷规则：被邀请人需完成 1 次拍照记录才算有效，同设备只算 1 次，单人奖励上限 180 天。

## 2.4 异常场景

| 场景        | 处理方式                                      |
| --------- | ----------------------------------------- |
| 拍照识别失败/模糊 | 提示"没看清，换个角度再拍或手动搜索"，保留手动录入入口              |
| 食物库查不到    | 提示"这是新菜？手动填热量或先跳过"，进入用户自定义食物（仅本人可见，标记待审核） |
| AI 服务超时   | 前端提示"AI 正在思考，稍后再问"，降级为预设 FAQ 回答           |
| 微信步数取不到   | 用 PAL 系数估算 NEAT，提示"绑定手环更精准"               |
| 支付中断      | 订单保留 15 分钟，超时自动取消并释放券，可重新下单               |
| 券过期/不可用   | 下单页灰显该券并标注原因（过期/不满足门槛/商家不支持）              |
| 网络异常      | 全局 toast，关键操作（记录、订单）本地缓存，恢复后重试            |
| 用户未授权订阅消息 | 引导跳转设置页开启，不阻断核心流程                         |
| 商家停业/已核销  | 订单详情提示"商家暂不可用"，支持退款入口（走客服工单）              |
| 邀请人达上限    | 提示"已达邀请奖励上限，感谢推广"                         |

## 2.5 验收标准（每条对应测试用例）

- 建档后首页热量账户环形图数值 = BMR×PAL - 已摄入 + 运动消耗 - TEF，误差 0。
- 拍照记录写入后，环形图"已摄入"与明细同步更新，无延迟超过 1 秒。
- AI 对话次数用完时，输入框上方展示"今日剩余 0 次，邀请好友解锁"，无法发送。
- 邀请 2 人（有效）后，用户权益变更为进阶版 90 天，首页/我的可见权益标签。
- 商家定价超出区间，后台保存时接口返回 400，前端提示"请在 ¥X-¥Y 之间定价"。
- 券核销码只能使用一次，重复使用返回"已核销"。
- 步数为 0 时，NEAT 用默认 PAL 估算；步数 > 0 时，按步数校准公式重算。
- 所有页面在 iPhone SE（小屏）与 iPad 上无横向溢出、无截断。

## 4.3 间距

4 点基准：xs=8rpx、sm=16rpx、md=24rpx、lg=32rpx、xl=48rpx。页面左右内边距 md（24rpx），卡片内边距 lg（32rpx），卡片之间间距 md（24rpx）。

## 4.4 圆角与投影

按钮默认 `--radius`；标签 `--radius-sm`；弹窗/底部弹层 `--radius-lg` 且顶部两角。卡片投影 `--shadow`，弹窗 `--shadow-lg`。

## 4.5 图标

图标库：使用 uni-icons 或 iconfont，尺寸 40rpx（列表图标）、48rpx（Tab）、64rpx（空状态插画）。配色跟随 `--text-2`，强调图标用 `--brand`。【假设】所有图标使用线性风格、2px 描边。

## 4.6 按钮

| 类型   | 样式                                              | 用途               |
| ---- | ----------------------------------------------- | ---------------- |
| 主按钮  | 底 `--brand`、字白、圆角 `--radius`、高 88rpx、字 `--t-28` | 核心操作（保存、立即支付、确认） |
| 次按钮  | 底白、边 `--border`、字 `--brand`                     | 次要（取消、稍后）        |
| 文字按钮 | 无底、字 `--brand`                                  | 内联操作（查看全部、换一个）   |
| 禁用   | 底 `#D1D5DB`、字白、不可点                              | —                |

按钮按压态：`opacity .85` 或加深底色。全宽按钮左右间距 md。

## 4.7 表单

标签在上、输入框在下；输入框高 88rpx、底白、边 `--border`、圆角 `--radius`、聚焦时边变 `--brand`。占位文字 `--text-3`。选择器（性别、活动水平）用分段控件或 Picker，选中态 `--brand` 底+白字。

## 4.8 表格

小程序内不做复杂表格，改用"卡片列表"呈现（每行一张卡，左标题右数值，底部操作）。管理后台 H5 用标准表格：表头 `--brand-dark` 底白字、行高 64rpx、斑马纹 `#F9FAFB`、悬停 `#F3F4F6`。

## 4.9 弹窗与提示

- 确认弹窗：标题 + 正文 + 次按钮"取消" + 主按钮"确认"，居中，圆角 `--radius-lg`，遮罩 50% 黑。
- 底部弹层：从底部弹出，顶部两角圆角，右上角关闭 X。
- Toast：黑底白字，居中偏上，1.5 秒自动消失。
- 加载：`wx.showLoading` 或骨架屏（灰块闪烁）。

## 4.10 导航与标签栏

顶部导航：返回箭头 + 标题居中 + 右侧可选操作，底白、边 `--border`。底部 5 Tab：图标 48rpx + 文字 20rpx，未选中 `--text-3`，选中 `--brand`，上边距 8rpx。

## 4.11 卡片

白底、圆角 `--radius`、投影 `--shadow`、内边距 lg。卡内第一行标题（左）＋可选操作（右），正文与辅助文字分两到三行，数值右对齐加大字重。

## 4.12 健康评分环与状态色

首页评分环：描边 12rpx，底色 `#E5E7EB`，进度色按区间：<60 红、60-80 琥珀、>80 绿。进度动画 800ms ease-out。状态点：🔴需关注、🟡建议、🟢正常、🔵服务（会员/复查）、🟠券即将过期。

## 4.13 暗色模式

【假设】首期不做暗色模式，全部浅色。若系统为深色，页面仍为浅色背景（不跟随），避免热量账户数字与绿环在深色下对比不足。

## 4.14 动效

页面切换右滑返回；卡片进场 300ms fade-up；环形图动画；按钮按压；下拉刷新标准菊花。不做复杂 Lottie。

## 6.3 关键模块设计

### 6.3.1 热量账户

- 每日快照：每天 0 点生成 `daily_snapshot`（日期、预算、摄入、消耗、缺口、步数），避免每次打开都重算。
- 写入触发：饮食记录新增/编辑/删除 → 重算当日摄入 → 更新环形图。运动记录同理。
- 预算 = BMR × PAL；TEE = BMR×PAL + EAT + TEF（TEF=摄入×10%）。
- 缺口 = 摄入 - TEE，负值为热量缺口（有利减重）。

### 6.3.2 视觉识别 + 知识库

- 食物库：`food` 表 1700+ 条，含热量、蛋白、脂肪、碳水、GI、分类；搜索走 PostgreSQL 全文检索 `tsvector` + 别名表 `food_alias`。
- 识别流程：上传照片 → COS → 视觉 API 返回候选类目 → 匹配 `food` 表 → 置信度 < 0.7 时让用户确认 → 写入记录。
- AI 对话：LangChain + Milvus/PGVector（【假设】首期用 PGVector 省一套组件）+ RAG 检索知识库；系统提示词固定：身份为"AI 饮食教练"、只答体重管理、超限/疾病类引导就医。

### 6.3.3 步数校准 NEAT

- 四层融合：状态选择（粗调）→ 微信步数（精调）→ 穿戴设备（微调，二期）→ 体重变化（终极校准，周度反推）。
- 校准公式：基础 NEAT = MET_state × 体重 × 非睡眠小时；步数校准：按每小时步频映射 MET（散步 2.5 / 快走 4.3 / 跑步 8.0），逐时累加得 NEAT_calibrated，与状态法结果加权（步数占比 0.6、状态 0.4，有权重>0 时）。

### 6.3.4 商家与价格区间

- 标准目录 `sku_catalog` 由平台运营维护，商家只选不选建。
- 商家定价时，后端校验 `price BETWEEN min_price AND max_price`，超出返回 400。
- 权重分 = 拉新贡献 40% + 券贡献 40% + 过程贡献 20%；前 20% 战略合作独家区域，前 50% 优选合作保护，连续零贡献清退。

### 6.3.5 券池

- 券统一入 `coupon_pool`，用户只能从邀请任务/平台补贴获得，不外发。核销码 UUID，唯一索引。
- 核销：商家扫码（或手动输入）→ 校验归属商家、未用、未过期、满足门槛 → 标记已用 → 释放订单锁定库存。

### 6.3.6 安全

- 认证：微信小程序 `code2session` 换 `openid`，签发 JWT（access 2h + refresh 7d）。
- 接口：HTTPS 全站；敏感操作签名；CORS 白名单；SQL 参数化（ORM 天然防注入）。
- 限流：全局 100 次/分钟/IP；AI 对话 20 次/分钟/用户；登录 10 次/分钟/IP。
- 内容安全：用户发帖/上传图走微信 `security.msgSecCheck` + `imgSecCheck`，违规进入审核队列。
- 隐私：手机号加密存储；默认匿名身份；删除账号级联清除可清除数据；日志脱敏。

## 6.4 部署架构

单机起步：Nginx + FastAPI（uvicorn 多 worker）+ PostgreSQL + Redis + Celery worker（异步任务）。COS 走外网。监控用 Prometheus + Grafana（资源/接口耗时），日志用 Loki（或文件 + 集中收集，【假设】首期落文件，Cron 打包上传 COS）。

## 6.5 第三方依赖清单

微信小程序 API（登录、支付、订阅消息、内容安全、步数）、腾讯云 COS、视觉识别 API、DeepSeek/通义千问、地图（LBS 用腾讯地图）、可选智能硬件 OpenAPI。

## 7.3 关键关系与约束

- 所有业务表带 `user_id` 的业务数据必须行级隔离（查询默认带 user_id 条件），防止越权。
- `daily_snapshot` 唯一约束 `(user_id, snapshot_date)`，幂等写入。
- `invite.invitee_id` 唯一：一人只能被邀请一次。
- 订单金额一致性：服务端重算 `pay_amount = total_amount - discount_amount`，不信任前端。
- 核销码唯一索引，防止重复核销。

## 7.4 归档策略

超过 2 年的 `meal_record`、`sport_record`、`ai_dialog` 按月分区归档到历史表 `xxx_archive_YYYYMM`，热表只留近期数据。首期数据量小可不实施，但表结构预留 `created_at` 便于后续分区。

# 第九部分：测试方案

## 9.1 测试分层

单元测试（后端 pytest，覆盖服务层与计算逻辑）≥ 70% 行覆盖；接口测试（pytest + httpx）；前端组件测试（Vitest + uni-app 测试库）；E2E（微信开发者工具自动化 + Playwright 测 H5）。

## 9.2 功能测试

- 建档：各字段边界（身高 0/200、体重 0/500、年龄负数）均校验。
- 热量计算：覆盖 5 种活动水平 × 男女 × 各餐摄入组合，结果对照 Excel 手算表（附件 `calorie_test_cases.xlsx`【假设】需自造一份 50 行用例）。
- 拍照识别：准备 30 张测试图（食堂餐盘 10、外卖 10、便利店 10），记录识别准确率、分量估算误差。
- 步数校准：模拟 0/3000/8000/12000/20000 步，校验 NEAT 落在合理区间。
- 商家定价：上边界、下边界、越界各一条，越界必返回 400。
- 券：过期、未达门槛、非本商家、重复使用各一条用例。
- 邀请：自邀请、同设备、重复绑定、达上限各一条。

## 9.3 兼容性测试

- 微信开发者工具：模拟 iPhone 6/7/8、iPhone X、iPhone 12 Pro、iPad、Android 主流机型。
- 真机：至少 2 台 iOS、2 台 Android；覆盖微信 8.x 与最新版。
- 管理后台 H5：Chrome、Edge、Safari 最新版 + 1920/1440/375 三档宽度。
- 网络：4G/弱网/断网，验证本地缓存与重试。

## 9.4 性能测试

- 单接口 P95 < 300ms（查询）、< 800ms（写+重算）。
- AI 对话 P95 < 3s，超时降级。
- 首页首屏（含账户重算）< 1.5s。
- 压测：100 并发持续 5 分钟，错误率 < 1%，无内存泄漏。
- 数据库：单表 100 万行下分页查询 < 500ms。

## 9.5 安全测试

- 越权：用用户 A 的 token 访问用户 B 的记录接口，必返 1002。
- SQL 注入：所有列表查询入参用 `' or 1=1--` 等 payload 测试，无异常返回。
- XSS：动态内容中插入 `<script>`，存储后展示必须转义。
- 内容安全：违规词、违规图触发审核拦截。
- 接口重放：相同请求 1 秒内发 10 次，仅首次成功。
- 支付：篡改 `pay_amount` 或重复回调，订单金额不变、不重复发货。

## 9.6 Bug 等级与处理

| 等级    | 定义                 | 修复时限   |
| ----- | ------------------ | ------ |
| P0 致命 | 数据错算、支付/核销漏洞、崩溃、越权 | 24 小时内 |
| P1 严重 | 主流程阻塞、AI 不可用、数据丢失  | 3 天内   |
| P2 一般 | 样式错乱、文案错、交互别扭      | 下个迭代   |
| P3 轻微 | 错别字、建议类            | 排期处理   |

## 9.7 上线通过标准（Go-No-Go）

- P0/P1 全部关闭，无遗留。
- 接口测试 100% 通过，单测覆盖 ≥ 70%。
- 性能达标，安全测试无高危。
- 冒烟用例 50 条全部通过。

## 10.1 环境

## 10.2 目录结构

```
/app
  /backend   FastAPI 源码
  /miniapp   uni-app 小程序源码
  /admin     Vue3 管理后台
  /deploy    docker-compose.yml、Dockerfile、nginx.conf
  /docs      本文档
```

## 10.3 Docker

- `Dockerfile.backend`：python:3.12-slim + 多阶段构建，非 root 运行，暴露 8000。
- `Dockerfile.miniapp`：node:20 编译 → nginx 托管静态 H5（小程序走 uni-app 编译命令，非 Docker）。
- `docker-compose.yml`：web(api)、db、redis、worker、nginx，卷持久化 `pgdata`、`redisdata`、`uploads`。

## 10.4 Nginx

- 80 强制跳 443；443 配 Let's Encrypt 证书（Certbot 自动续期）。
- `/api/` 反向代理到 FastAPI `127.0.0.1:8000`；`/admin/` 代理前端静态；`/uploads/` 代理媒体。
- 静态资源缓存 7 天，HTML 不缓存；限流 `limit_req_zone` 100r/s。

## 10.5 数据库迁移

Alembic：新增字段/表先写迁移脚本 → 测试库验证 → 生产执行前备份 → 执行 → 验证行数。

## 10.6 回滚

Git Tag 打版本；构建镜像带 `git short sha` 标签。回滚：`docker compose down && docker compose up -d --scale` 切回上一镜像，数据库迁移若不可逆需另备反向脚本（【假设】首期迁移只做可加字段、不删不改列，保证可回滚）。

## 10.7 监控与日志

- 监控：Prometheus 拉取 `/metrics`（接口 QPS、延迟、错误率、热量账户计算耗时、AI 调用成本）；Grafana 面板。
- 日志：JSON 格式，含 `request_id` 链路追踪；落盘 `/var/log/app/`，Cron 每日打包上传 COS，保留 30 天。
- 告警：服务不可用 5 分钟、错误率 > 5%、磁盘 > 80%、AI 日成本超预算时企业微信/邮件告警。

# 第十三部分：零提问默认决策规则

> 开发中遇到任何不确定、资料缺失、两可的情况，**按本规则立即选一个默认方案继续，不停工**。不要停下来问，不要在代码里写 TODO 等确认。

## 13.1 通用默认

- **信息缺失**：按【假设】处理，选业界最常见方案，并在代码注释/PR 说明里写"默认决策：xxx"。不要阻塞。
- **字段类型**：数值一律 `NUMERIC` 带精度（金额/热量 2 位，克 1 位）；时间用 `TIMESTAMPTZ`（带时区）；状态用 `SMALLINT`（0/1/2），不用布尔表达多状态。
- **排序/分页**：列表默认按 `created_at DESC`，每页 20 条，前端可传 `page`/`page_size`（上限 100）。
- **空值**：数据库字段默认允许 NULL（除主键/业务必填），用 `COALESCE` 兜底 0。
- **金额单位**：全部统一为**元**（人民币），保留两位小数；展示时千分位。
- **重量单位**：全部统一为**克**（g）；展示时自动换算（<1000 显示 g，≥1000 显示 kg）。
- **热量单位**：全部统一为 **kcal**；展示为整数。
- **时间**：服务端存 UTC+8（Asia/Shanghai），返回 ISO8601 字符串带 `+08:00`。
- **命名**：表名/字段名 snake_case；接口路径 kebab-case；接口字段 snake_case；前端变量 camelCase。

## 13.2 交互默认

- 未登录访问需登录页：先跳登录，登录成功回跳原页。
- 加载 > 300ms：必须展示 loading（骨架屏或 loading 图标）。
- 列表为空：插画 + 一句引导 + 主按钮。
- 请求失败：toast 提示，可重试的给重试按钮。
- 删除操作：二次确认弹窗。
- 表单提交：提交中按钮置灰，防重复提交。
- 图片加载失败：占位灰块 + 默认图标，不裂图。
- 浮点数比较：用 `round(x, 2)` 后比较，避免精度问题。

## 13.3 业务默认

- 未填活动水平：默认 2（久坐），PAL 1.4。
- 未填目标：默认"减脂"，每周 0.5kg。
- 步数为 0 或取不到：用 PAL 系数估算 NEAT，不报错。
- AI 识别置信度 < 0.7：必须让用户确认/修正。
- AI 服务不可用：降级返回预设 FAQ，不卡死。
- 券不满足门槛：灰显并标注原因，不隐藏。
- 商家定价越界：后端 400 拒绝，前端提示区间。
- 邀请判定：被邀请人完成 1 次拍照记录算有效；同设备、自邀请均无效。
- 权益发放：邀请数达档位**次日**批量任务发放（用定时任务，不实时），失败重试 3 次。

## 13.4 代码与工程默认

- 提交信息：`feat:` `fix:` `refactor:` `test:` `docs:` `chore:` 前缀。
- 分支：`main`（生产）+ `develop`（开发）+ feature 分支，PR 合入 develop。
- 环境变量：`.env.example` 提交，真实 `.env` 不入库；生产密钥走服务器环境变量。
- 日志：统一 JSON，含 `request_id`；不打密码、token、手机号原文。
- 异常处理：统一异常处理器，返回标准错误码，不向前端抛堆栈。
- 数据库：所有写操作走事务；查询默认带租户/用户条件。
- 第三方依赖：锁定版本（poetry lock / package-lock），不锁主版本导致大升级。
- 代码风格：Python 用 ruff + black；前端用 eslint + prettier，提交前自动格式化。
- 如遇到技术方案确实需要确认且影响大的（如是否引入 pgvector）：默认选最简单的实现（【假设】首期存 jsonb 占位），在 PR 中说明后续可替换，**先做出来再优化**。

## 13.5 一句话原则

**能跑 > 完美。先交付可用版本，再迭代。** 所有"更好但慢"的选择，一律延后到 P1/P2。
